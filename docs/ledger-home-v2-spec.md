# 規格：帳務首頁 v2 — 監測帶與月份帳目分離

狀態：**待實作**。來源＝2026-08-15 Yen 口述需求（附帳務首頁截圖）＋本文件的規格化。
基準＝分支 `feature/ledger-home-redesign`（handoff 01 已完成的版本）。

---

## 1. 這次要解決什麼

目前帳務首頁把兩種時間尺度的東西混在同一頁、同一組數字裡：

- **監測性資訊**（現在的財務體質）：淨額帶、未來四週現金、收支分析
- **期間性資訊**（這個月發生了什麼）：收入／支出明細

兩者現在都掛在同一個月份選擇器下，導致數字語意不一致（見 §2 的既有缺陷）。

v2 的主張：**上半部＝全帳戶最新監測狀態（不受月份影響），下半部＝該月份的實際收支明細（受月份影響）**。
未結的約定（未收／未付）從首頁移走，整合進「應收款／應付款」兩個模式。

---

## 2. 必須一併修掉的既有缺陷（不是新需求，是現況就錯的）

**現況**：`AllView.tsx` 的「帳面淨額」是這樣算的：

```
incomeSettled  ← 受月份篩選（只有這個月的已收分錄）
incomeUnsettled ← 不受月份篩選（全帳戶所有未結應收）
netFace = (incomeSettled + incomeUnsettled) - (expenseSettled + expenseUnsettled)
```

也就是說「帳面淨額」把**本月已收**和**全部未收**加在一起，這個數字不對應任何真實概念——
切換月份時它會變，但變的只有一半，另一半是全帳戶常數。使用者無法從畫面得知這件事。

v2 把監測帶改成全帳戶後，這個矛盾自然消失（兩邊都變成全帳戶）。
**實作時要確認淨額帶的所有輸入都不再帶 `month`**，不能只改一半。

## 3. 版面結構（桌機）

```
┌─────────────────────────────────────────────────────────┐
│ 監測帶（全帳戶最新狀態，不受月份影響）                    │
│  ├ 淨額帶：帳面淨額／實收實付淨額／差距                   │
│  ├ 未來四週現金                                          │
│  └ 收支分析                                              │
├─────────────────────────────────────────────────────────┤
│ ‹ 2026-08 ›   ← 月份選擇器搬到這裡（見 §3.2）             │
│ 本月收支明細（受月份影響）                                │
│  ├ 收入列表（固定高度＋內部捲動＋視覺化判讀）             │
│  └ 支出列表（固定高度＋內部捲動＋視覺化判讀）             │
└─────────────────────────────────────────────────────────┘
```

### 3.1 監測帶：不受月份影響

- 淨額帶、未來四週現金、收支分析三塊，資料來源一律是**全帳戶當前狀態**，與 `?month=` 完全無關。
- 需要一個明確的標示，讓使用者知道這一段不跟著月份走。建議在監測帶右上角放一行 11.5px faint 文字：
  「全帳戶即時狀態 · 不受下方月份影響」。
  **這句不能省** —— 否則使用者切月份看到上半部不動，會以為畫面壞了（靜默失效）。
- 「已收付」的部分改為全帳戶累計。實作上是把 `AllView` 查 `ledger_entries` 的
  `monthRange` 條件拿掉（監測帶專用的那份查詢）。

### 3.2 月份選擇器搬到列表區

**理由**：月份現在只管下半部。若仍留在頁面最上方，使用者按下去會看到頂部數字不動，
這是典型的「控制項作用範圍不明」問題。搬到列表區標頭旁邊，作用範圍就自我說明了。

- 位置：本月收支明細的區塊標題列，與標題同一行右側。
- 保留現有的 `?month=` URL 驅動與 Server Component 重渲染機制，不改互動模型。

### 3.3 篩選器的作用範圍需要決策

現在的篩選（歸屬／分類／發票／內外帳）是全頁生效。監測帶改成全帳戶後：

- **建議**：篩選器一併移到列表區，只作用於下方列表，與月份同一組。監測帶永遠是未篩選的全帳戶狀態。
- 理由同 §3.2——監測帶是「體質儀表板」，被篩選過的體質不是體質。

**此項待 Yen 確認**（見 §7）。

## 4. 未結約定移到「應收款／應付款」

### 4.1 改名

| 現況 | 改為 |
|---|---|
| 應收未收 | **應收款** |
| 應付未付 | **應付款** |

- URL 參數值 `?mode=receivable` / `?mode=payable` **維持不變**（內部識別碼，改了會讓既有連結失效）。
- 只改顯示文字。涉及 `page.tsx` 的模式列標籤，以及所有指向這兩個模式的文案。

### 4.2 未結約定卡片整體搬移

目前 `MixedList.tsx` 裡的「未收約定 N 筆」／「未付約定 N 筆」區塊（含空心黃框卡片、
約定日顯示、結清／作廢按鈕）**整組移到** `ReceivablesView`。

- 現行 `ReceivablesView` 是桌機表格＋手機卡片的舊樣式，用 `MixedList` 那套空心描邊卡片取代，
  視覺語言統一（實心＝已收付、空心＝未收付的幾何編碼維持）。
- 保留現有的 `StatusButtons`（含 handoff 01 加的結清防呆二次確認）。
- 保留「應收應付不受月份篩選」的既有行為（本來就對，這是餘額不是流水）。

### 4.3 首頁列表只剩已收付

`AllView` 的下方列表移除 `unsettledItems`，只留 `settledItems`。
`MixedList` 的 props 相應簡化（或直接改名為 `SettledList`）。

## 5. 收支明細列表（下半部）

### 5.1 固定尺寸 ＋ 內部捲動

**注意：這推翻 handoff 01 的第 5 項**（原本明訂「固定高度 560px 面板取消，列表跟著頁面捲動」）。
v2 改回固定高度，理由是版面結構變了：監測帶現在是常駐儀表板，
列表若跟頁面捲動會把監測帶推出視野，失去「一眼看到體質」的目的。

- 收入／支出兩欄固定同高，欄位尺寸不隨資料筆數變動。
- 高度：建議 `480px`（實作時以「監測帶＋列表在 1080p 筆電不需捲頁」為驗收標準微調）。
- 內部捲動使用既有的 `.app-scroll`（`globals.css` 已有玻璃色捲軸樣式）。
- 兩欄即使筆數差很多也維持同高，切篩選／換月份時版面不跳動。

### 5.2 視覺化判讀（本規格最需要確認的一項）

需求原話：「總收支列表 要有個別的視覺化判讀呈現，讓使用者有更多的資訊吸收判斷」。

**建議方案 A — 每列佔比條**（推薦，最小新 UI、直接沿用既有設計語言）

每一列在金額下方加一條 2px 高的細條，寬度 ＝ 該列金額 ÷ 本欄本月總額。

- 一眼可判讀：相對大小、有沒有異常大筆、前幾筆是否高度集中。
- 顏色沿用方向色（收入綠／支出紅），不引入新色。
- 沿用既有規則：欄首標「比例以本欄自身 100% 計」，禁止跨欄比長度。
- 金額旁可加 `佔 12.4%` 的 11px 灰字（或僅 hover 顯示，避免視覺過載）。

**替代方案 B — 欄首分類彙總條**
在每欄頂端放一條分段長條，顯示前 3 大分類／專案佔比，其餘歸「其他」。
回答「錢主要從哪來／花到哪去」，但看不出個別列的相對大小。

**替代方案 C — 當月日流水 sparkline**
在欄首放一條迷你折線，顯示該月每日的收／付金額分布。
回答「錢什麼時候動的」，但與列表逐列資訊沒有直接對應。

三者可疊加，但**建議先只做 A**——它最貼近「個別的視覺化判讀」這個原話（重點在「個別」＝逐列）。

### 5.3 列表的資料範圍要標清楚

下方列表現在只含**已收付**分錄，且**只含該月份**。
與監測帶的數字沒有任何一個會相等。因此：

- 區塊標題必須明寫範圍，例如「本月已收付明細 · 2026-08」，不可只寫「收入／支出」。
- 欄底小計文案要寫「本月已收 $X」，不可只寫「小計」——避免被誤讀成帳面總額。
- **這是「不可靜默」的必要條件**：兩組數字在同一頁但語意不同，沒標清楚就是在誤導。

## 6. 手機版

- 監測帶維持在最上方，不受月份影響（同桌機）。
- 月份選擇器同樣搬到列表區。
- 收入／支出維持既有的 tab 切換（一次只看一邊）。
- **固定高度在手機上待確認**：小螢幕上固定高度容易讓可視列數過少（可能只剩 3–4 筆）。
  建議手機維持頁面捲動、只有桌機固定高度。此項列入 §7 待確認。
