# 報表中心 · 形狀探索 Brief（給設計端）

## 這份文件是什麼

**這不是 handoff。** 跟 `ledger-home-design-handoff.md`、`project-home-design-handoff.md` 是不同性質的東西——那兩份是「功能做完了、資料對過了，來做視覺打磨」。這份相反：

> **功能還沒做。這一輪要你決定的是「形狀」——資訊架構、組織方式、路徑設計。**

原因：報表中心的「數字是什麼」已經定了（見下方第 3 節），但「怎麼組織才看得懂」還沒有人知道，包括提出需求的人自己。這種事紙上談會失準，必須看到東西才判斷得出來。

所以這一拍的產出**不是成品，是一個讓人看了會說「喔，原來我要的是這個 / 不是這個」的東西**。

## 1. 這一拍的紀律（請務必照做）

**要**
- 快。半天以內，不是三天
- 醜。用最陽春的方式呈現，能看懂結構就好
- 假資料。不用接資料庫，寫死在檔案裡即可
- 可以一次給多個方案。三個粗糙方案，遠勝一個精緻方案

**不要**
- 不要做得漂亮。做得漂亮會讓人捨不得丟，形狀就這樣被鎖死了——那正是這一拍要避免的事
- 不要碰 `web/app/boss/ledger/` 底下任何正式檔案。另開一個獨立的路由或 HTML 檔，怎麼髒都行
- 不要接真實資料查詢
- 不要在這一拍調色、對齊、做動效

**判斷你做完了沒有的標準**：把東西給老闆看，他能指著說「這個對」「這個不對」，而不是說「都可以」。

## 2. 背景

### 這是什麼

音響工程公司的內部帳務系統（1 老闆 + 3–5 員工，已上線、有真實資料）。帳務模組現在有六個分頁：金流監測 / 已收付 / 應收款 / 應付款 / 月結 / **報表中心**。

報表中心目前只有一張陽春的月/季/年損益表，這一輪要把它擴成帳務系統的**收斂點**。

### 使用者

- **老闆一人**。不是給會計師用的操作介面（會計師只收匯出的檔案）
- 桌機為主、手機也會用
- 不懂會計術語，但非常清楚自己公司的錢

### 他來這一頁是要回答哪些問題（這是領域事實，不是視覺傾向）

1. 這個月 / 這一季 / 今年，公司賺不賺錢
2. **哪個案子賺、哪個案子賠**
3. 報稅期到了，要給記帳士的數字在哪
4. 零用金花去哪了
5. 看到一個數字覺得怪 → 這筆錢到底是什麼

第 5 點是貫穿全部的：**任何彙總數字都要能追回原始帳目**。這是硬性要求，不是加分項。

### 兩件必須成立的事

- **能直接列印 / 存成 PDF**，而且印出來要是能交給記帳士或銀行的文件品質（不是螢幕截圖的感覺）
- **所見即所得**——螢幕上看到的內容，就是印出來的內容

## 3. 已定的口徑（唯讀事實，不要動）

這些是「數字是什麼意思」的決定，已經拍板。你在設計時把它們當成給定條件。

### 3.1 四份報表的內容

| 報表 | 內容 | 期間粒度 |
|---|---|---|
| **損益表** | 營業收入 / 營業費用 / 營業損益 / 營業外及個人項 / 本期淨額，含上期與去年同期比較、增減 %、各項佔營收 % | 月・季・年 |
| **專案損益** | 每個案子：收入 − 直接成本 − 代墊 − 人力分攤 = 毛利、毛利率 | **整案期**（不被月/季切割） |
| **營業稅申報彙總** | 銷項金額 / 銷項稅額 / 進項金額 / 進項稅額 / 應納稅額，含待開發票清單 | **兩個月一期**（台灣申報週期） |
| **零用金彙總** | 依人、依案兩種切法 | 月・季・年 |

注意三張表的期間粒度不一樣，這是真實的業務差異，不是可以統一掉的東西。

### 3.2 收入分類規則

- **營業收入** = 案件收款、其他收入
- **不算營業收入** = 借款/資本、投資、健檢（這些是業外與老闆個人項，要另計，不進營業損益）
- 轉帳手續費是真實現金流出，必須獨立成一列，且必扣

### 3.3 人力成本怎麼算（人天分攤）

```
人天成本 = 該員工當月月薪 ÷ 當月出勤天數（打卡）
各案分攤 = Σ 歸屬到該案的人天 × 人天成本（一天去兩個案場 → 各 0.5 人天）
未分攤池 = 未歸屬的出勤日 × 人天成本（內勤、庫房、雜務、忘了填）

恆等式：Σ各案分攤 + 未分攤池 = 該員工當月月薪
```

**「未分攤池」是這套算法的可信度溫度計**——如果某月 60% 的薪資都落在未分攤池，那所有專案毛利數字都只有很低的參考價值。

## 4. 資料語意鐵律（不可違反）

視覺與結構可以大改，這幾條不能破。**這些不是保守，是因為破了會讓報表說謊。**

### R1 · 「已收付」與「應收未收」絕不可合成同一個數字

系統是現金收付制。一筆錢先記「應該收」、之後實際收到再記一次，合併就會被算兩遍。畫面上任何地方要呈現，必須「已收 X + 未收 Y」分開講清楚，不可寫成一個模糊的合計。

### R2 · 營業損益與本期淨額是兩個數字，不可只留一個

「本業賺不賺錢」跟「今年整體進出多少」是不同的事實。借款進來會讓後者好看，但前者才是老闆該看的經營狀況。兩個都要在。

### R3 · 「未分攤池佔比」不可被縮小、變灰、收進次要區域

它決定了整張專案損益表可不可信。**多顯眼是你的設計判斷（見待決問題 4），但「可以藏起來」不在選項裡。**

### R4 · 資料稀疏時，數字不可以照樣顯示得很有自信

某月完全沒有案場歸屬資料 → 該月的專案毛利要明白顯示「不含人力成本」，不可以只印一個看起來很正常的毛利率。寧可露醜，不准默默少算。

同理，任何維度視圖都必須有**「未歸類」殘差行**，讓 `Σ各分項 + 未歸類 = 帳本總數` 這個恆等式在畫面上成立。沒掛案子的帳目要明列，不可以從分項裡消失。

### R5 · 讀取失敗不可偽裝成「沒有資料」

查詢出錯時不可以顯示 $0 或空清單——「查不到」跟「沒有」是完全不同的事實。現行做法是整塊紅框說明，維持這個原則。

### R6 · 顏色不可以是唯一的區分方式

色盲安全是硬性要求。正負、已結未結等區分要有第二編碼（形狀、紋理、文字標記）。

### R7 · 畫面上不可出現內部術語

不可出現 `to_issue`、`in_repair`、`reimbursement` 這類程式碼名稱或資料表名稱，一律用中文業務語言。（見 `ui-conventions.md` §9）

## 5. 待決的形狀問題（這一拍要撞出答案的）

**以下五題我刻意不給傾向。** 給了傾向你就會往那邊做，那這一拍就白做了。

### Q1 · 四份報表怎麼組織？

分頁切換？單頁往下堆？選單切換？還是根本不該是「四份報表」這種結構？

補充脈絡：報表中心本身已經是帳務模組六個分頁裡的第六個。所以這裡的組織方式會是「分頁裡的分頁」，這件事本身就值得質疑。

### Q2 · 期間選擇器怎麼處理？

四份報表的期間粒度不同（月/季/年 vs 整案期 vs 兩個月一期）。共用一個選擇器？各自獨立？還是有別的解法？

### Q3 · 列印預覽是不是一個獨立狀態？

兩種路線：
- 螢幕版直接就是列印版（真正的所見即所得，但螢幕體驗會受紙張限制）
- 螢幕版與列印版分離，有一個「預覽」狀態（螢幕自由，但要處理兩者的一致性）

**這題的答案會決定整個列印功能怎麼實作**，是五題裡技術影響最大的一題。

### Q4 · 「未分攤池佔比」放哪、多顯眼？

R3 規定它不能被藏起來，但「不能藏」跟「該多大聲」之間有很大的空間。它是常駐指標？還是超過某個門檻才跳出來？

### Q5 · 下鑽的路徑長什麼樣？

點一個數字 → 看到組成它的原始帳目 → 然後呢？

現況：明細住在另一個分頁（「已收付」），有自己的篩選系統。所以下鑽會離開報表中心。這樣對嗎？還是明細該在報表中心裡就地展開？返回路徑怎麼設計才不會讓人迷路？
