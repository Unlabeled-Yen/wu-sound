## 交接說明

你要設計的是「專案管理」這個分頁——**公司所有人(老闆 + 3–5 位現場人員)共用同一個
介面**,用來管理每個案子底下的待辦、工作日誌、以及跟這個地點有關的長期知識。

**先讀這兩份**,是硬性約束不是參考:

| 文件 | 為什麼要讀 |
|---|---|
| `docs/ui-conventions.md` | 全站互動一致性契約。第 9 節(畫面不出現內部術語)、第 5 節(空狀態必須有 CTA)、第 10 節(列表容器規則)這次特別重要 |

## 1. 一句話定義

> 每個案子有一個工作面,上面有這個案子還沒做完的事、做過的事、以及這個地方值得
> 記住的事;全公司的人都看得到、都能寫。

---

## 2. 三個前提(這次改動的來源)

### 2.1 不分角色

老闆與現場人員看到的是同一個介面、同一份資料。沒有審批、沒有分派、沒有權限分級。

> **工程端要注意**:現有系統是 `/boss`(桌機、亮玻璃、三層浮起面板)與
> `/staff`(手機、深色玻璃、底部分頁)兩套殼。這一頁兩邊的人都要進得來,
> 所以它要嘛同時掛進兩套殼、要嘛開一條中性路由。這件事**尚未決定**,
> 但不影響你設計——見第 9 節。

### 2.2 以案子為入口

案子清單 → 點進一個案子 → 看到這個案子的全部。

不是「一個大看板混所有案子」,是**一案一工作面**。

### 2.3 兩種裝置,同一個頁面

同一個人可能早上在辦公室用桌機排事情、下午在工地用手機記事情。這不是
「桌機版 + 手機版」兩套設計,是**同一個東西在兩種寬度下的兩種形態**。

手機那一端的使用者長這樣,設計時腦中要有他:

- 站在梯子上,單手,另一手扶著支架
- 手是髒的,可能戴著工作手套
- 戶外正午陽光直射
- 現場在試音,很吵
- 客戶站在旁邊等他回話
- 地下室或郊區場館,網路很差

## 3. 三種內容物件(封閉集合,不會再增加)

使用者不需要背它們的名字,但**畫面必須讓人一眼看出現在看的是哪一種**。

| | 一句話判準 | 有狀態嗎 | 會過期嗎 | 掛在哪 | 例子 |
|---|---|---|---|---|---|
| **待辦** | 「有人要去做一件事」 | 有 | 會 | 案子 | 三號廳左邊喇叭支架要鎖緊 |
| **工作日誌** | 「今天發生了什麼」 | 無 | 是流水帳 | 案子 | 今天裝完二號廳,收工五點 |
| **場地知識** | 「下次來還要知道的事」 | 無 | **不會** | **地點** | 三號廳吊點只能吃 80 公斤 |

### 場地知識為什麼掛在「地點」不是「案子」

案子會結束,地點不會。三年後回到同一個場館,當年那條「吊點只能吃 80 公斤」還要查得到。
而你們的既有規則是「一案一性質,同客戶既有安裝又辦活動請開兩個案子」——
所以同一個實體場館本來就會散在多個案子裡。

**對設計的影響**:在案子頁面上看到的場地知識,視覺上要能表達
「這條不屬於這個案子,是屬於這個地方的」。它在案子結束後還會留著,
而且會出現在下一個同地點的案子裡。

**這是這次最容易做錯的地方**——如果把它畫成「案子底下的備註」,整個回憶功能就死了。

## 4. 資訊架構

```
專案管理
├── 案子清單            ← 分頁入口,所有案子
└── 案子詳情            ← 點進去之後,這是設計重心
    ├── 基本資料(既有:案子名、客戶、性質、啟用狀態、設備在場數)
    ├── 待辦            ← 四欄工作面
    ├── 工作日誌        ← 時間序,append-only
    ├── 場地知識        ← 跟著地點走,跨案子
    └── 出車前檢查表    ← 依案子性質展開成待辦
```

案子詳情裡這五塊怎麼組織(頁內分頁?單頁捲動?側欄?)**由你決定**,
但要注意兩種裝置寬度下都成立。

## 5. Trello 機制清單(給你發想的積木)

Trello 的架構是這次的參照對象。以下逐項拆開,標明我們的取捨與理由。
**「用」不代表要長得像 Trello**——是說那個機制要解決的問題我們也有。

### 5.1 直接沿用

| Trello 機制 | 它解決什麼問題 | 我們怎麼用 |
|---|---|---|
| **看板 Board** | 一個工作範圍的容器 | 一個案子 = 一個工作面 |
| **看板牆** | 所有看板的入口 | 案子清單頁 |
| **列表 List(位置即狀態)** | 拖到哪就是什麼狀態,不用填表單 | 四欄,見 5.4 |
| **卡片 Card** | 一件事的最小單位 | 一則待辦 |
| **標籤 Label** | 彩色、可命名、可多選、可篩選 | 6 個:急/叫料/施工/客訴/報價/保養 |
| **成員頭像** | 卡片上直接看到誰負責 | **自動帶入建立者**,不手動指派(見 5.5) |
| **到期日** | 逾期會自己變色跳出來 | 選填;「卡住・等料」自動設 3 天後 |
| **檢查清單 Checklist** | 卡片內的子項 + 進度條 | 出車前預備事項 |
| **範本 Template** | 一鍵複製成新的一組 | 檢查表範本,綁在「案子性質」上 |
| **附件與封面 Cover** | 照片變成卡片的視覺主體 | **很重要**,見 5.3 |
| **留言 Comment** | 卡片內的時間序討論 | 卡住要寫在等什麼;決定要留痕 |
| **篩選 Filter** | 依標籤/人/到期日即時濾 | 案子內篩 |
| **搜尋** | 跨卡片找字 | **要跨案子**,這是「查找」的落點 |
| **封存 Archive** | 移出視線但不刪除 | 完成 14 天後自動封存 |
| **活動記錄 Activity** | 誰在什麼時候做了什麼 | 要有,但收起來,不佔主視覺 |

### 5.2 Trello 有、但我們刻意不用

| 機制 | 為什麼不用 |
|---|---|
| **收件匣 + 專人分類** | 記的人多數就是做的人。中間插一層分類是純成本,而且是整套最先斷掉的一環——現場的人記了三次沒人理,第四次就不記了 |
| **「進行中」欄** | 站在梯子上沒人會為了把卡片往右移一格而掏手機。卡片上有頭像,誰在做本來就看得到 |
| **指派他人 / 審批** | 違反「誰記誰做」 |
| **三級優先權** | 結果一定是全部填最高,等於沒分級,還多一次點擊。只做「急」一級 |
| **卡片相依關係、甘特圖、進度百分比** | 現場記事沒這種需求,加了沒人維護 |

### 5.3 照片:比 Trello 更重要

Trello 的封面是選配。**在我們這裡照片是主要輸入方式之一**——站在梯子上拍一張比打字快得多,
而且「三號廳左邊那個支架」用講的講不清楚,拍下來一秒就懂。

設計時把照片當成一等公民,不是附件。一張卡有照片跟沒照片,可能是兩種不同的卡片形態。

### 5.4 四欄工作面

| # | 欄位 | 誰在動 | 規則 |
|---|---|---|---|
| 1 | 要老闆決定 | 記的人自己判斷後直接丟 | 只放「要花錢 / 對客戶承諾 / 要調別人時間」三類 |
| 2 | 待辦 | 任何人 | **預設落點**,一句話就成立 |
| 3 | 卡住・等料 | 執行的人 | 必須留言寫「在等什麼」 |
| 4 | 完成 | 執行的人 | 拉進來就結束,不用另外回報 |

第 3 欄是這一行的必要欄:音響工程最常見的停滯是等貨、等場地、等客戶決定。
沒有它,這些卡片會混在「待辦」裡,讓人以為只是還沒做,實際上是根本動不了。

**四欄是上限,不得再加。** 每多一欄就多一次「這該放哪」的猶豫。

### 5.5 誰記誰做

記錄的人預設就是負責的人。建卡當下自動成為成員,不需要任何人指派或分類。

唯一的例外是第 1 欄——但那個判斷**也是記的人自己做**(他當然知道自己能不能拍板),
不是別人幫他分類。

這是**預設不是禁令**:別人要幫忙處理某張卡,直接把自己加進去就好,不需要流程。

### 5.6 拖曳:手機上要有替代方案

「位置即狀態」是 Trello 最好的地方——改狀態只要一個手勢,不用開表單。

但**手機上跨欄拖曳很難**,單手、戴手套、站在梯子上更難。你需要設計一個
非拖曳的改狀態方式,而且它不能是「開啟卡片 → 找到狀態欄位 → 選 → 儲存」那種四步流程。

### 5.7 Trello 沒有的兩塊(要你發明)

**這兩塊是這次設計真正的難題。Trello 沒有現成答案可抄。**

#### (a) 場地知識

Trello 的一切都在某個列表裡、都有狀態、都會完成。但場地知識:

- 不屬於任何一欄
- 不會完成
- **跨案子存在**,案子結束了它還在
- 會一直累積,三年後可能有 50 條

**難題**:

> 累積 50 條知識,進場前只想看 5 條。哪 5 條?怎麼讓人快速掃?

排序、分群、釘選、折疊、依設備/廳別分類——都是你可以用的工具,選哪個是設計決策。
唯一的鐵律是:**不能讓人捲三十秒才找到重要的那條。**

#### (b) 工作日誌

Trello 的活動記錄是**系統產生**的(「某某把卡片移到完成」)。我們要的是
**人寫的**日誌(「今天裝完二號廳,客戶臨時要求把主喇叭往左移兩米」)。

它不屬於任何一張卡,它是「這個案子今天發生了什麼」。

**難題**:日誌跟待辦在同一個案子頁面上,怎麼共存而不互相淹沒?
一個案子跑三個月會有 60 則日誌,但只有 5 張未完成的卡。

## 6. 要設計的畫面

| # | 畫面 | 優先 |
|---|---|---|
| A | 案子清單 | 必要 |
| B | 案子詳情 — 待辦四欄工作面 | 必要 |
| C | 案子詳情 — 場地知識 | 必要 |
| D | 卡片詳情(留言、檢查清單、照片) | 必要 |
| E | 案子詳情 — 工作日誌 | 次要 |
| F | 出車前檢查表(展開成待辦) | 次要 |
| G | 跨案子搜尋結果 | 次要 |

每個畫面都要有手機與桌機兩種寬度。

### 關於 F 的一個迴路,不要漏掉

> 現場踩到坑 → 記成場地知識 → **一鍵升級成該性質的檢查表項目** → 下次同性質的案子
> 出車前自動出現 → 不再踩

這條迴路讓系統隨時間變聰明,而且變聰明的來源是現場的人,不是任何自動化。
**「升級成檢查表項目」這個動作要顯眼且低摩擦**,否則迴路不會被走,這功能就只是一個
比較好看的記事本。

## 7. 已知的設計張力(我沒有答案,想聽你的)

### 7.1 以案子為入口 vs 現場要快

「以案子為入口」在辦公室是對的:要找一個案子的事,從案子進去最直覺。

但現場那個站在梯子上的人,他腦中冒出「這個支架鬆了」的當下,**多一步「先選案子」
就可能讓這筆紀錄流失**。

可能的方向(你來判斷,或提出更好的):

- 頂層保留一個不分案子的「快速記」入口,事後再歸案
- 系統依打卡地點/當天班表猜案子,猜錯可一鍵改
- 案子清單頁上每一列就有「記一筆」

**這題我認為是這次設計成敗的關鍵。** 架構上以案子為入口是對的,但如果現場因此少記
一半的事,那這個架構就贏了道理輸了實際。

### 7.2 場地知識跟工作日誌,在使用者心裡真的是兩種東西嗎?

資料上必須分開(一個永久、一個流水),但介面上要不要讓人感覺是兩種,是開放的。

## 8. 硬性限制

摘自 `ui-conventions.md`,加上現場特有的。**破例可以,但要寫理由。**

1. **畫面上不出現內部術語。** 不能是 `open`、`site_id`、資料表名。要寫「未完成」「案子」。
2. **空狀態必須有可執行的按鈕**,不能只寫「還沒有資料」。
3. **危險動作(刪除、作廢)兩步確認**,且第一步要輸入原因。
4. **錯誤就地顯示**,不要整頁錯誤、不要瀏覽器彈窗。
5. **長列表要有最大高度 + 內滾 + 固定表頭**,不要整頁一根捲軸。
6. **觸控目標 ≥ 48px**(戴手套點得到)。
7. **主要動作放拇指區**(手機螢幕下半),不要右上角。
8. **戶外陽光下要讀得到。** 關鍵資訊不能只靠低對比的次要色。

## 9. 失敗要看得見(單獨列)

這是本專案一貫的原則:**壞了要吭聲,不准靜默失效。**

至少這四種要設計出可見狀態:

| 情境 | 不可接受的做法 |
|---|---|
| 沒網路,紀錄還沒上傳 | 顯示成已儲存 |
| 照片上傳失敗 | 靜靜地少一張照片 |
| 系統猜不出是哪個案子 | 隨便挑一個最像的填上 |
| 內容過長被截斷 | 看起來像完整內容 |

**離線暫存要不要做,由你評估後提建議。** 如果做,「還沒上傳」跟「已上傳」
必須在視覺上是兩種明確不同的狀態,不能只差一個小灰點。

## 10. 明確不要設計的東西

| 不做 | 理由 |
|---|---|
| 角色分流、權限分級 | 全員共用同一介面 |
| 指派他人、審批流程 | 違反「誰記誰做」 |
| 甘特圖、時間軸、進度百分比 | 沒人會維護 |
| 通知中心、動態牆 | 5 個人的團隊不需要 |
| 三級優先權 | 只做「急」一級 |
| 任何顯示金額的地方 | 金額走報價系統,不進這裡 |
| 新增案子的表單 | 案子主檔是既有功能,沿用 |

## 11. 成功標準

不是主觀評分,是可以拿原型實測的:

| # | 檢驗 | 及格 |
|---|---|---|
| 1 | 手機、戴手套、單手,記一件事 | ≤ 10 秒,≤ 3 次觸控 |
| 2 | 手機上把一張卡從「待辦」改成「完成」 | ≤ 2 次觸控,不用拖曳 |
| 3 | 進場前在場地知識裡找到關鍵那條 | ≤ 5 秒 |
| 4 | 桌機上看一個案子,說得出「還有什麼沒做」 | ≤ 3 秒 |
| 5 | 戶外陽光下 | 主要資訊讀得到 |
| 6 | 網路斷掉 | 使用者知道自己斷線了 |

第 1 關跟第 4 關會互相拉扯(見 7.1),**兩關都要過**才算成功。

## 13. 背景:為什麼參照 Trello 而不直接用

先前評估過直接用 Trello(規格見 `trello-board-spec-v1.md`,驗證計畫見
`trello-board-verification-v1.md`),結論是**機制對、平台不對**:

- 場地知識要跨案子存在,但 Trello 一張卡只能待在一個列表
- 工作日誌需要人寫的案子級日誌,Trello 的活動記錄是系統產生的
- 檢查表要綁既有的「案子性質」,外部工具接不到

所以我們拿它的機制,不拿它的平台。這也是為什麼第 5 節寫得那麼細——
**那些機制是被驗證過好用的,不要重新發明;第 5.7 那兩塊才是需要你創造的。**
