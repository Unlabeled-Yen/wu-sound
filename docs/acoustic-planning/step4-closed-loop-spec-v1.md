# 第四步規格 v1 — AI 選設備 ↔ 計算器閉環驗證(2026-08-03)

## 為什麼

AI 選設備目前**對物理完全是盲的**。送進模型的品項提示只有四個欄位:

```
CatalogHint = { name, brand, item_type, category }    // lib/ai-quote.ts:8
```

沒有音壓、沒有靈敏度、沒有功率。所以它挑 CODA HOPS8i 是因為型錄裡有這個名字、類型對得上,**不是因為算得出來這款在那個場地打得到**。實測時它挑得「內行」,是因為型錄本身就是雇主常用的那批器材,不是因為它驗證過。

這一步把確定性的計算器接進來當守門員:**AI 提配置 → 引擎驗證 → 不通過就退回重挑**。

關鍵在於驗證那一步是確定性的。AI 不參與判定,只接收判定結果。

## 核心設計

### 流程

```
老闆的需求描述
   ↓
① 場地參數解析(第二步的解析器)→ 深度、目標音壓等
   ↓
② AI 選設備(維持現狀,ai-quote.ts 不改判斷邏輯)
   ↓
③ 確定性驗證(spl-budget.ts)→ 通過 / 不足 / 無法驗證
   ↓
④ 不足 → 把「哪裡不足、差多少 dB」回饋給 AI,重挑(上限 2 次)
   ↓
⑤ 結果連同判定一起呈現給老闆,由他決定採不採用
```

### 判定必須三態,不得塌成兩態

這是本規格最重要的一條。判定結果只能是:

| 判定 | 條件 | 呈現 |
|---|---|---|
| **通過** | 規格齊全,且算出的建議投射距離 ≥ 場地深度 | 綠色,標明餘裕多少 |
| **不足** | 規格齊全,但建議投射距離 < 場地深度 | 紅色,標明差多少公尺/dB |
| **無法驗證** | 配置中任一喇叭缺 `max_spl_db` 或 `spl_ref_distance_m`,或場地深度未知 | **黃色,明確列出是哪幾項缺什麼** |

**「無法驗證」絕對不得顯示為「通過」,也不得隱藏。** 目前 114 個品項的規格全是空的([第三步](step3-spec-data-spec-v1.md)才會補),所以這個功能剛上線時**大多數情況都會落在「無法驗證」**——這是正確且必要的行為,不是缺陷。

這條規則是有前車之鑑的:標案雷達曾因為把「查不到」當成「沒有」而講得太肯定,後來才改成四態欄位狀態。同一個錯不重犯。

### 驗證邏輯(確定性,不經 AI)

新增 `web/lib/quote-acoustic-check.ts`:

```
輸入:AI 建議的品項清單(含品項庫 id)+ 場地參數(深度、目標音壓)
處理:
  1. 取出配置中 item_type 為「喇叭」的品項
  2. 任一品項缺 max_spl_db / spl_ref_distance_m → 回「無法驗證」,列出缺的品項名
  3. 場地深度未知 → 回「無法驗證」
  4. 對每支喇叭呼叫既有的 computeSplBudget(),取 recommendedMaxThrowM
  5. 取配置中最遠可達距離(多支同型視為同一組,不做疊加加成)
  6. 與場地深度比較 → 通過 / 不足
輸出:三態判定 + 數值明細 + 缺項清單
```

沿用 `lib/spl-budget.ts` 既有函式,**不重寫任何聲學公式**。餘裕類參數(動態餘裕、安全餘裕)取計算器的同一組預設值,並在結果中明列用了什麼值,讓老闆能判斷這個驗證嚴不嚴格。

**多支喇叭不做聲壓疊加加成**(第 5 點)。疊加牽涉相位與擺位,現有模型不涵蓋;寧可保守判定,不要給一個算得出來但不成立的數字。此限制須寫在結果的警語裡。

### 回饋重挑(第 ④ 步)

- 上限 **2 次**重挑,超過即停,把最後一次結果連同「試了 N 次仍不足」一起呈現。
- 每一次重挑都**可見**(顯示「第 2 次建議」),不做背景靜默重試。
- 回饋給 AI 的內容只有事實:哪支喇叭、算出多遠、場地多深、差多少。**不告訴 AI 該換成什麼**,那是它自己的工作。
- 判定為「無法驗證」時**不重挑**(重挑也不會變成可驗證),直接呈現。

### 成本

最壞情況是原本 1 次呼叫變 3 次。因此:

- 重挑只在「不足」時觸發,「通過」與「無法驗證」都不重挑
- 驗證本身是本地計算,不花錢
- 上限寫死 2 次,不可設定,避免無限迴圈燒錢

## 與 ADR-0002 的關係

[ADR-0002](../adr/0002-ai-never-sets-price.md) 訂的是「AI 選品項、系統定價格」。本步驟把同一條界線延伸到物理:**AI 選品項、系統驗物理**。AI 的職責範圍完全沒有擴大,只是它的產出多了一道確定性把關。

`SuggestedLine` 型別**不新增任何欄位**。驗證結果是另一個獨立結構,不混進 AI 的回傳裡。

## 資料落點

驗證結果是否入庫,取決於要不要事後追溯:

- **建議第一版不入庫**。它是選設備當下的輔助判斷,場地參數改了結論就變,存下來反而容易變成過期的假事實。
- 若日後要做「這張報價當初驗過嗎」的稽核,再另開欄位討論。

## 驗收條件

| ID | 條件 | 方式 |
|---|---|---|
| L-01 | 規格全空的現況下,判定為「無法驗證」並列出缺項,**不得顯示通過** | auto |
| L-02 | 手動填一組足夠的規格 + 淺場地 → 判定「通過」,餘裕數值正確 | auto |
| L-03 | 同上但場地深度加大到打不到 → 判定「不足」,差距數值正確 | auto |
| L-04 | 「不足」觸發重挑,且重挑次數上限為 2 | auto |
| L-05 | 「無法驗證」不觸發重挑 | auto |
| L-06 | 重挑過程對使用者可見,非背景靜默 | browser |
| L-07 | 結果明列所用的餘裕參數值與「未計疊加」警語 | browser |
| L-08 | AI 呼叫失敗 → loud 顯示,不得把失敗當成「無法驗證」混過去 | browser |
| L-09 | `SuggestedLine` 型別未被加入任何物理或價格欄位 | auto(型別檢查) |

L-01 與 L-08 是本步驟的核心驗收:一個防「缺資料被當成通過」,一個防「呼叫失敗被當成缺資料」。三種狀態必須互相區分得開。

## 不做

- 不讓 AI 參與判定,不讓 AI 覆寫判定結果。
- 不做聲壓疊加、相位、地面反射、空氣吸收建模。現有引擎的自由場假設就是上限,寫在警語裡而不是偷偷補一個係數。
- 不自動採用 AI 的重挑結果。最終仍由老闆逐行確認(維持 Phase 3 的人工確認節奏)。
- 不做電學驗證(用電量、瓦數×場地)。該公式雇主仍未提供,見 `docs/open-questions.md`;公式到位後可作為第二個驗證器接進同一個三態框架。
