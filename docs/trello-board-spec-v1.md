# 現場待辦看板規格書 v1(2026-08-15)

用 Trello 做現場即時待辦的收集與追蹤。這份是**規範文件**:每條需求有編號,
驗證文件 `trello-board-verification-v1.md` 逐條對應。

目前定位是**試跑**,不是最終決定。試跑結果決定要續用 Trello 還是收回自建(第 9 節)。

**用語**:「必須」= 不做就不算完成;「應該」= 建議但可依現場調整;「不做」= 刻意排除,
不是遺漏。

## 1. 目的與界線

### 1.1 要解決的問題

員工在現場冒出一件事要記下來——「三號廳左邊喇叭支架鬆了」「客戶說想再加兩支立麥」
「這場的電源孔不夠」。目前這些話散在通訊軟體裡,案子要收尾時沒有一個地方能問
「這案還有什麼沒做」。

### 1.2 這不是專案管理,是現場記事

專案管理是「事情怎麼被分派與追蹤」,現場記事是「事情怎麼被記下來、讓別人也看得到」。
門檻要低到接近零,否則兩週後所有人會回去用通訊軟體傳訊息,看板變成墓碑。

### 1.3 共用看板的價值只有三件

既然是誰記誰做,自己記在手機備忘錄也能「自己記得」。共用看板多出來的價值只有:

- **交接**:人請假或換班,他腦子裡那幾件事別人接不到。
- **案子收尾**:結案前要問「這案還有什麼沒做」,得有地方能查。
- **老闆的視野**:想知道現場堆了什麼,不用一個一個問。

這三件**都不需要任何人做分類**,只需要事情寫在同一個地方。這是本設計的界線:
共用的是「寫在哪」,不是「誰來管」。

### 1.4 明確不做的事

| 不做 | 理由 |
|---|---|
| 收件匣 + 專人每天分類 | 記的人多數就是做的人,中間插一層是純成本,且是最先斷掉的一環 |
| 工時、成本、進度百分比 | 那些在自家系統,不在這裡 |
| 甘特圖、里程碑、相依關係 | 現場記事沒有這種需求,加了只會沒人維護 |
| 細部權限控管 | 5 個人的團隊做權限是純成本 |
| 三級優先權 | 結果一定是全部填最高,等於沒分級,還多花一次點擊 |

## 2. 核心原則:誰記誰做

**R-P01(必須)** 記錄的人預設就是負責的人,不需要任何人分類或指派。

**R-P02(必須)** 唯一例外是「這件不是我能決定的」,限以下三類:

- 要花錢(叫料、加購、外包)
- 對客戶的承諾(要不要加做、要不要另外報價)
- 要調動別人的時間

**R-P03(必須)** 上述判斷由**記的人自己做**,直接丟到「要老闆決定」,不經過第三人。

設計理由:前者是記的人做一個他本來就會做的判斷(他當然知道自己能不能拍板),
後者是硬給某個人加一個每天的義務。初版那個「每天要清收件匣」的義務量體大又枯燥,
斷掉是遲早的事——現場的人記了三次沒人理,第四次就不記了。

**R-P04(應該)** 「誰記誰做」是**預設不是禁令**。別人要幫忙處理某張卡,直接把自己
加進成員即可,不需要任何流程。

## 3. 跟現有系統的關係

系統裡**已經有**一個叫「專案管理」的頁面(`/boss/sites`),但那是**案子主檔**。
三者不重疊:

| | 管什麼 | 在哪 |
|---|---|---|
| `/boss/sites`「專案管理」 | 有哪些案子(名稱、客戶、性質、啟用狀態、設備在場數) | 自家系統 |
| Trello「現場待辦」 | 案子底下有哪些事**還沒做** | Trello |
| `/staff/worklog`「工作記錄」 | 現場**發生過**什麼(事後留痕) | 自家系統 |

**R-X01(必須)** 卡片標題的案子名必須照 `/boss/sites` 的案子名寫,不得另創簡稱。
這是之後能否收回自建的關鍵——名字對得起來才接得回去。

**R-X02(必須)** 不得拿 `/staff/worklog` 工作記錄當待辦用。工作記錄是「我做了什麼」,
待辦是「還沒做的事」,兩者方向相反。

## 4. 看板結構

**R-B01(必須)** 只開一個看板,名稱「現場待辦」,全公司共用。

不要一個案子開一個看板。3–5 人跨案子跑,一人一天可能碰三個場;案子各自有板的話,
現場的人要先想「這件事屬於哪個板」才能記,這個猶豫就是流失點。

> 例外:接到橫跨數月、任務上百的大案時,該案單獨開板是合理的。日常不用。

**R-B02(必須)** 看板可見性設為工作區私密,不得公開。

**R-B03(必須)** 全員(老闆 + 3–5 位員工)皆為一般成員,都能建卡、移卡、改別人的卡。

---

## 5. 列表(四欄)

**R-L01(必須)** 列表由左至右固定為四欄,順序不得調換:

| # | 列表名 | 誰在動 | 規則 |
|---|---|---|---|
| 1 | `要老闆決定` | 記的人自己判斷後直接丟 | 只放 R-P02 那三類 |
| 2 | `待辦` | 任何人 | **預設落點**,誰記誰做,一句話就成立 |
| 3 | `卡住・等料` | 執行的人 | 自己拉,卡片必須留言寫「在等什麼」 |
| 4 | `完成` | 執行的人 | 自己拉,不用另外回報 |

**R-L02(必須)** 不設「收件匣」。預設落點就是「待辦」,不經過任何人的手。

**R-L03(必須)** 不設「進行中」。站在梯子上沒人會為了把卡片往右移一格而掏手機,
那是跟分類同一類的成本;而且卡片上有成員頭像,誰在做本來就看得到。

**R-L04(必須)** 「卡住・等料」保留。音響工程最常見的停滯是等貨、等場地、等客戶決定。
沒有這欄,這些卡片會混在「待辦」裡,讓人以為只是還沒做,實際上是根本動不了。

**R-L05(必須)** 四欄是上限,不得再加。每多一欄就多一次現場「這該放哪」的猶豫。

## 6. 標籤

**R-T01(必須)** 標籤共 6 個,全部**必須命名**(只有顏色沒人記得住):

| 標籤 | 顏色 | 用途 |
|---|---|---|
| `急` | 紅 | **只有一級**,不做高中低 |
| `叫料` | 黃 | 類型 |
| `施工` | 藍 | 類型 |
| `客訴` | 橘 | 類型 |
| `報價` | 綠 | 類型 |
| `保養` | 紫 | 類型 |

**R-T02(必須)** 標籤全部選填。誰記誰做的前提下,標籤主要是給老闆掃看板用的,
不是給記的人用的;現場不填也完全成立。

**R-T03(必須)** 不得拿標籤標案子。案子會一直新增,標籤一膨脹,現場那個下拉選單
就沒人想滑。

**R-T04(必須)** 案子維度用卡片標題前綴:`[案子名] 一句話`

例:`[誠品信義] 三號廳左喇叭支架鬆了`

Trello 搜尋框打「誠品」就能撈出該案全部卡片,效果一樣,維護成本零。

---

## 7. 卡片

**R-C01(必須)** 唯一必填欄位是標題。格式 `[案子名] 一句話`。

**R-C02(必須)** 成員由自動化在建卡時自動填成建卡的人(R-A01),不需手動點。

**R-C03(應該)** 其餘欄位皆選填:

| 欄位 | 誰填 | 備註 |
|---|---|---|
| 照片(附件) | 記的人 | 現場最常用的輸入,站在梯子上拍一張比打字快 |
| 描述 | 記的人 | |
| 標籤 | 記的人 | |
| 到期日 | 記的人,自己覺得需要才設 | 「卡住・等料」由自動化代設(R-A03) |
| 檢查清單 | 只有多步驟工項才開 | |

**R-C04(必須)** 卡片移入「卡住・等料」時,必須留言寫「在等什麼」。
沒寫的話這張卡對別人是無效資訊。

**R-C05(應該)** 在「待辦」放一張範本卡片(template card),描述裡貼上本節那張表。

## 8. 輸入管道

這是整套設計成敗的地方。三條路都開。

**R-I01(必須)** 手機主畫面小工具 — 一鍵新增卡片,直接落到「待辦」。

**R-I02(必須)** 看板專屬 Email 地址 — 主旨變標題、內文變描述、附件變附件。
**這條可以接現有的語音介面**(`voice-lab/`、`/staff/capture`):語音轉文字後寄過去
就變卡片。

**R-I03(應該)** iOS 捷徑 — 「按一下、講一句話、自動建卡」,走 R-I02 的 Email 管道實作。
對站在梯子上的人這是唯一可行的輸入法。

R-I02、R-I03 是這套能不能活下來的關鍵。只有 R-I01 的話,採用率會卡在
「願意掏手機開 app 的人」。

> **已知風險**:Email 管道進來的卡片,建卡者是寄信的信箱,R-A01 的自動指派可能對不上。
> 驗證項 V-F05 專門測這件事;對不上的話走 V-F05 的退路。

## 9. 自動化(Butler)

以「觸發 → 動作」描述。**Trello 介面的實際字串與這裡的措辭可能不同,依畫面為準。**

**R-A01(必須)** 卡片建立 → 自動把建卡的人設為成員。
*理由*:誰記誰做,建卡當下就該有主,不用手動指派。

**R-A02(必須)** 卡片加入「要老闆決定」 → 通知老闆。
*理由*:這是唯一真的需要別人動作的一欄。

**R-A03(必須)** 卡片移到「卡住・等料」 → 設到期日 = 3 天後。
*理由*:防止卡片死在這一欄。到期會自己冒出來,而不是靜靜躺著。

**R-A04(必須)** 每天定時 → 封存「完成」中超過 14 天的卡片。
*理由*:沒這條,兩個月後看板會因為完成欄堆兩百張卡而變慢、變難看。這條最容易被忽略。

> Butler 在免費方案有每月執行額度上限,**實際數字未確認**,以 Trello 當前方案頁為準。
> 上述四條都是低頻規則,以我們的量體推測應在額度內;試跑期須留意有無額度警告(V-T04)。

## 10. 資料落地

Trello 是外部雲端服務(Atlassian)。

**R-G01(必須)** 可以放:工地待辦內容、現場照片、案子名。

**R-G02(必須)** 不得放:報價金額、客戶聯絡資料、收據影像、薪資與工時。
這些留在自家系統。

原則跟收據辨識那條治理線一致:**辨識得出個人或金額的東西不外流**。

**R-G03(必須)** 「要老闆決定」那一欄天生會誘發寫金額(「客戶問加兩支立麥多少錢」)。
規則是**寫事情,不寫數字**;金額回自家系統的報價系統處理。

## 11. 已知的最大風險

改成誰記誰做之後,「沒人清收件匣」這個風險消失了,但剩下一個:

**老闆不看「要老闆決定」那一欄。**

現場的人把需要拍板的事丟上去,三次都沒回應,第四次就不丟了——之後再怎麼改軟體都
救不回來,因為那是信任的問題,不是功能的問題。

好消息是這個風險比初版小得多:它只涉及**一個人**、只涉及**一欄**,而且那一欄的量體
會很小(絕大多數事情記的人自己就處理掉了)。

這個風險由驗證項 V-T03 量測。

## 12. 之後如果要收回自建

這套架構可以原封不動搬進 `wu-sound-fde`,設計不用重來:

| Trello | 對應資料表 |
|---|---|
| 看板 Board | (只有一個,不需要表) |
| 列表 List | `todo_status` 列舉,四態 |
| 卡片 Card | `todos`(標題、描述、site_id、owner、due、status) |
| 標籤 Label | `todo_labels` 多對多 |
| 成員 Member | 沿用現有 users |

`owner` 預設 = 建立者,對應 R-P01。

收回自建的好處是待辦能跟 `sites`、打卡、支出接起來,可以直接回答
「這個案子還有幾件事沒收尾」。試跑期用 Trello 是為了**先驗證人的習慣**——
如果人不會用,自建也一樣沒人用,那就不值得寫。
