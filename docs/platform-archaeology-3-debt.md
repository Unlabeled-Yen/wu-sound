## 🔴 會造成資料錯誤或誤導使用者的問題

1. **設備「淘汰不可逆」的警語是假的**——淘汰確認框寫「無法直接還原」,但
   同頁的「移動」功能完全不擋已淘汰狀態,可直接把淘汰設備移回在庫/在場,
   且不會有任何特殊標記。(設備庫存)

2. **設備狀態機沒有任何轉移限制**——DB 與程式碼都只驗證「on_site 才可有
   site_id」,不限制哪個狀態能轉去哪個狀態。維修中可以直接跳去案場、
   任何狀態都可以跳回任何狀態。(設備庫存)

3. **編輯報價單明細的「存回價目表」勾選框預設打勾**——編輯單一報價單的
   折扣價,若沒注意勾選框,會靜默覆寫全域品項庫售價,影響所有未來新報價單
   與套組材料化價格。(報價系統)

4. **`day_site_allocations.hours` 從未被寫入,但 UI 文案宣稱它是損益依據**
   ——`/boss/clockins` 頁面明講「未分攤的日子會在專案損益報表列為內勤/庫房」,
   但全庫沒有任何報表在讀這張表。這句話是假的功能承諾。(專案管理與現場,
   跟帳務模組發現的「人力成本未進損益」是同一個坑,但這裡多了具體的誤導性
   UI 文案)

5. **員工打卡與工作記錄各自有一套「今天去了哪個案場」的選單,互不核對**
   ——worklog 表單選一次、下班打卡又選一次(寫進不同表),系統不會提示兩者
   矛盾。這是老闆特別點名疑慮的「重複工作流」在現場模組的具體案例。
   (專案管理與現場)

## 🟡 維護困難

**設備庫存**
- 「編輯基本資料」有兩套實作(server action + API route),diff 判斷邏輯不一致
- 「淘汰設備」邏輯被複製貼上兩份(server action + DELETE route)
- `GET /api/equipment` 對員工開放且不過濾已淘汰,跟 staff 頁面自己過濾的邏輯不一致(此端點目前無人呼叫,是潛在債務)

**報價系統**
- `quotes.site_id`(為報價↔實際毛利對照預留)完全沒有程式碼讀寫,是明確標註但未完成的地基
- 品項庫 8 個聲學規格欄位只能被計算工具讀,沒有任何寫入介面,只能直接動 DB
- `/api/catalog` 沒有 `include_inactive` 參數(對比 `/api/bundles` 有),品項一旦下架就無查詢介面能再看到
- 品項庫 UI 完全沒有上架/下架操作按鈕(對比套組有清楚的停用按鈕)
- 已停用的套組詳情頁沒有存取限制、沒有「重新啟用」按鈕

**專案管理與現場**
- worklogs / clockins 都沒有編輯或刪除入口,打錯只能新增一筆蓋過去,錯誤資料永久累積
- `/api/sites` 的 GET 不回傳 `category_id`/`customer_name`,老闆維護的案場分類/客戶資訊對第一線員工端完全隱形
- `day_site_allocations` 允許一天勾選多個案場,但工時如何在多案場間分配沒有輸入介面
- `worklogs.site_id` 在 DB 層允許 NULL,但只在 API 層強制必填,schema 與應用邏輯不一致
- 補打卡沒有任何順序/配對防呆,可能靜默改變已核對過的當月工時,且無 diff 紀錄

**使用者/權限/LINE/voice-lab**
- 權限判斷散落在 30+ 支 API route 各自內聯重複寫 `session.role !== 'boss'`,無共用 helper、無 middleware
- Session 內嵌 role 且 14 天內不查 DB,老闆停用/改權限某員工,對方的舊 session 仍可能繼續有效到過期為止
- voice-lab-chat 沒有角色或案場區分,任何登入者可對所有案場下指令(目前是 Lab 2 實驗階段的刻意簡化,無 TODO 標記日後要補)

## ⚪ 純粹冗餘(不影響資料正確性)

- 報價單「標記已送出」按鈕與狀態下拉選單是兩條並行路徑做同一件事(報價系統)
- `quotes.note`、`catalog_items.note` 兩個備註欄位 DB/API 支援但 UI 無輸入框(報價系統)
- CSV 匯出總額未套用稅率,跟列印頁/編輯頁顯示的總價對不上(報價系統)
- `equipment.serial_number` 無 unique constraint,同序號可重複建檔(設備庫存)
- `equipment.quantity` 與「單件可追蹤」語意有隱性衝突,無法表達部分調度(設備庫存)
- `LineMessage` type union 兩個分支重複同一 discriminant,型別定義冗餘(LINE)
- `GET /api/equipment` 是死碼,repo 內無人呼叫(設備庫存)
- 標案監測三個頁面各自重寫一次環境變數檢查與錯誤訊息模板,無共用抽象層(標案監測)
- `/boss/tenders/agencies`(機關經營名單)是孤兒路由,沒進任何導覽選單

## 正面觀察(交接文件模板要求的基準線,不是只挑錯)

幾個 agent 都在報告裡主動指出值得保留的做法,一併記錄避免後續重建時被誤刪:

- 聲學計算模組整體乾淨,職責單一,陣列設計器有 2081 組 golden 資料撐著核心公式,測試投資量級遠高於其他模組
- 品項庫的「進價絕不外流、售價可為 null 走待補價」是刻意的資訊邊界設計,不是疏漏
- LINE webhook 對簽章驗證、逐事件錯誤隔離、推播失敗降級(不擋主流程)等防禦性設計紮實
- `boss/users/actions.ts` 是全平台唯一每個變更都經過共用權限 helper 且完整寫 audit_log 的模組,可以當其他模組補齊時的參考範本
- voice-agent 系列檔案(session/工具schema/LLM轉接/主狀態機/STT)職責切分清楚,無明顯重疊
- voice-agent-session.ts 用記憶體儲存對話是有意識的技術債,作者已在註解與 UI 行為(重置提示)裡明講,不是隱藏的坑
- 標案監測刻意把商業邏輯/演算法隔離在外部私有服務,repo 本身只放 UI 殼,這是有意識的架構決定(repo 是公開的)
