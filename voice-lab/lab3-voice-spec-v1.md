## 1. 核心衝突:語音沒有按鈕(這是 Lab 3 最重要的設計題)

原始 handoff §5.3 寫的是:

> 使用者明確肯定(「對」「可以」「沒錯」)→ 帶 token 呼叫寫入工具
> 模糊回應(「嗯…」「應該吧」)→ 視為未確認,再問一次

**Lab 2 刻意否決了這個做法**。實作硬化那一節寫得很清楚:不讓 LLM 有機會判斷使用者是否同意,
寫入只認 `{action:'confirm'}` 這種結構化事件。實測也證明這個判斷是對的——
Kimi 連「這筆還沒寫入」都會講成「已經幫你記了」,要它分辨「對」和「應該吧」是同一類的賭注。

語音情境下按鈕不存在。所以要先想清楚:**當初要守的到底是什麼?**

> 要守的鐵律是「**確認與否不由 LLM 判斷**」。
> 按鈕只是這條鐵律在螢幕上的實作方式,不是鐵律本身。

這個區分決定了三個選項的取捨:

| 方案 | 做法 | 守不守得住鐵律 | 代價 |
|---|---|---|---|
| **A 螢幕確認** | 語音輸入,但確認仍要看卡片按鈕 | ✅ 完全守住 | 工地戴手套/手髒時就是用不了,語音的價值砍半 |
| **B 口令確認** | 複述後,使用者必須說出白名單內的**精確詞**(「確認」「沒錯」「對」);由 runtime 做**字串比對**,不是模型判斷 | ✅ 守得住——判斷的是程式不是 LLM | STT 誤聽、旁人講話誤觸;需要信心度門檻 |
| **C 語意判斷** | 讓 LLM 判斷使用者是否同意 | ❌ 破功 | 就是 Lab 2 花力氣擋掉的東西 |

**建議:A + B 雙軌。** 有螢幕就用螢幕(預設),免手情境才開 B,且 B 要加三道硬化:

1. **白名單字串比對**:只有「確認」「沒錯」「對」「可以」這幾個詞算數,由 runtime 比對正規化後的
   STT 文字,**LLM 完全不參與這個判斷**
2. **信心度門檻**:STT 信心度低於閾值一律當沒聽到,重問一次(handoff §8 已有此要求)
3. **完整複述**:複述必須唸出結構化欄位(專案全名/動作/內容/日期+星期幾),
   而不是模型自由發揮的一段話——這份欄位 Lab 2 已經生好了,直接唸即可

**否決 C,無論如何。** 這是架構紅線,跟「工具面沒有寫入工具」同一級。

## 2. 架構選擇:先不要 Pipecat

handoff §7 指定 Pipecat(Python)。**Phase 1 建議不要**,理由是專案約束而非技術偏好:

- wu 這套系統的部署約束是**免費 hosting**。Pipecat 要一個常駐的 Python 服務 + WebSocket,
  免費層放不下,而且會把目前「一個 Next.js app」的部署模型變成兩個服務。
- Phase 1 的主場景是**口述紀錄**(handoff §6 自己說了「口述紀錄場景對延遲要求較寬」),
  不是需要插話打斷的即時對談。

**建議路徑**:

| 階段 | 做法 | 成本 | 能做到 |
|---|---|---|---|
| **3a(先做)** | 瀏覽器內建 `SpeechRecognition` + `SpeechSynthesis`,後端完全不動 | 0 元 | 講話輸入、唸出回覆、驗證語音情境下的確認流程 |
| **3b(視 3a 結果)** | 伺服器端 streaming STT(供應商待選)+ 熱詞表 | 依用量 | 專有名詞正確率、延遲預算 |
| **3c(Phase 2)** | Pipecat + barge-in | 需常駐服務 | handoff §6 的完整延遲預算 |

3a 的價值不是「做出產品」,是**用最低成本驗證第 1 節那個確認設計到底順不順**。
如果口令確認在真實工地行不通,3b/3c 投再多都沒用。

**3a 的已知限制,不要假裝沒有**:

- 只能在 Chrome 系瀏覽器跑,而且要連 Google 的辨識服務(等於語音會離開本機——
  這跟 Kimi 收據辨識同一類的資料流向問題,上線前要老闆知情)
- 不支援熱詞 boosting,所以「磐頂」「放樣」「木作」會辨錯
- 沒有 VAD 參數可調、不能插話打斷

**辨錯專有名詞的緩解**:Lab 1 的 `search_projects` 本來就是模糊比對,
STT 把案名聽錯時多半仍能搜到候選,再由實體對齊追問補救。**這是既有設計的紅利,不用另外做。**

## 3. 範圍

### 做(3a)

- 測試頁加麥克風鈕:按住講話 → 辨識文字填進輸入框 → 送出(走現有 `/api/voice-lab/chat`)
- 回覆用瀏覽器 TTS 唸出來;**confirming 狀態唸的是結構化欄位,不是模型那句話**
- 免手模式開關:開啟後,confirming 狀態接受口令確認(白名單字串比對 + 信心度門檻)
- STT 空白/低信心 → 「沒聽清楚,再說一次」,不進 LLM(handoff §8)

### 不做

- 不做 barge-in(handoff §7 明講 Phase 1 不做,但選型不得阻擋 Phase 2)
- 不做熱詞表(3b 才有意義——瀏覽器 STT 不吃)
- 不做離線佇列、不做正式員工介面(Lab 4)
- 不改 Lab 1 契約、不改 Lab 2 的 agent runtime 邏輯

## 4. 驗收(對齊 handoff §9,依 3a 範圍調整)

1. 30 句真實情境語句唸過(紀錄、查詢、模糊實體、不支援操作、救難),工具選擇正確率 ≥ 95%
2. **口令確認硬化有效**:對著麥克風說「應該吧」「嗯…」不會寫入;說「確認」才會
3. **旁人講話不會誤觸**:confirming 狀態下播放無關對話,不得寫入
4. 專有名詞辨錯時,實體對齊仍能救回來(案名唸錯 → 仍搜到候選 → 追問選擇)
5. 錯誤情境:麥克風權限被拒、辨識空白、網路斷線 → 都要有明確提示,不得靜默

## 5. 四件事(2026-08-18 Yen 確認)

1. **確認方式:A+B 雙軌**。有螢幕用螢幕確認(預設);免手情境開口令確認
   (白名單字串比對,不讓 LLM 判斷)。
2. **3a 的資料流向:正式給員工用之前要先讓老闆點頭**——跟 Kimi 收據辨識同一類治理問題,
   語音會送到 Google 這件事,上線前要讓實際決定者知情同意。**動工前置**:3a 開發本身
   (測試階段)不受阻,但「正式開放給員工用」這個開關,要等這個點頭動作完成才能打開。
3. **先做 3a**:瀏覽器內建 `SpeechRecognition`,不跳過去直接選付費的伺服器端 streaming STT。
   0 元先驗證第 1 節那個確認設計順不順,專有名詞辨錯有 `search_projects` 模糊比對接住,
   不是致命傷。
4. **裝置:員工自己的手機瀏覽器**,不是公司配發的統一裝置。

   **這題的答案直接放大 3a 已知限制裡的一條**:3a 只能在 Chrome 系瀏覽器跑,
   iOS Safari 的 `SpeechRecognition` 支援度差(見「3a 的已知限制」小節)。員工自己的手機
   意味著裝置組合裡**一定會混到 iOS**——這不是驗證階段可以先不管的邊角情況,是正式
   會撞到的真實使用者。**動工時要明確處理**:iOS Safari 偵測到不支援時,語音入口
   要有清楚的降級提示(退回打字,不是靜默失效、不是空白按鈕),不能假裝所有裝置都一樣。
