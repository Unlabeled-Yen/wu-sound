# Lab 2 腳本化對話案例(spec §7 驗證計畫)

**用途**:Lab 2 沒有 Lab 1 那種契約測試(這裡驗的是對話品質,不是接口),改用這 8 個案例手動跑過。
**跑法**:`/voice-lab-chat`(登入後直接開網址,沒掛在導覽上)。

**前置**:`.env.local` 需要
```
ANTHROPIC_API_KEY=<既有>
VOICE_API_KEY=<既有>
VOICE_ACTOR_USER_ID=<既有>
VOICE_TOOLS_BASE_URL=http://localhost:3000   # Lab 2 新增
```
缺任何一個,頁面會回 503 並講出缺哪個(loud,不會假裝 AI 答不出來)。

跑之前先確認 migration `009_voice_tasks_proposals.sql` 已套用,否則工具會回 503「資料表尚未建立」。

---

## 判讀方式

每則 agent 訊息底下有一行灰字:狀態(追問中/等你確認/已回覆)+ 這一輪呼叫過的工具鏈,
失敗的工具會顯示 `工具名✗ERROR_CODE`。這行就是稽核線索,不用去翻 log。

**只要 [確認寫入] 沒被按下,資料庫就不該有新資料**——這是每個案例的共同驗收條件。

## 案例

| # | 情境 | 輸入 | 預期行為 |
|---|---|---|---|
| 1 | 單一動作、專案明確 | 「幫我在磐頂那個案子記一筆,木作進場前先放樣」 | 工具鏈 `search_projects → propose_log_note`;出現確認卡片,欄位為 專案/動作/內容;按確認後回「已記錄到『<完整案名>』的工作記錄」;DB 出現 worklog |
| 2 | 專案名 0 筆候選 | 「幫我在不存在的案子記一筆」 | 狀態「追問中」,明講找不到、問要不要換說法,並告知新增專案要用系統介面;**不出現確認卡片** |
| 3 | 多筆候選 | 用一個會命中 2 筆以上的關鍵字(例如「教會」) | 狀態「追問中」+ 候選按鈕;點一顆之後接得上原本要記的內容,不用重講 |
| 4 | 取消 | 案例 1 走到確認卡片後按 [取消] | 回「已取消,沒有寫入任何東西」;DB 無新資料;之後再按不到那張卡的按鈕 |
| 5 | 模糊肯定 | 走到確認卡片後,**用打字**回「應該吧」 | 舊提案作廢(不會被當成同意),agent 重新確認一次;DB 無新資料。這一案驗的是「確認只走按鈕、不解讀文字語意」 |
| 6 | 相對日期 | 「磐頂下週三要交圖,幫我開個任務」 | 確認卡片的「期限」欄是絕對日期 YYYY-MM-DD,且 agent 複述時也講絕對日期(對照今天是幾號自己算一次) |
| 7 | 不支援的操作 | 「幫我把上一筆的金額改成三萬」 | 明確回覆不支援、請用系統介面;**不呼叫任何寫入提案** |
| 8 | 多輪指代 | 案例 1 完成後接「再幫我記一筆,水電明天進場」 | 工具鏈**沒有** `search_projects`(沿用上一輪的 project_id);確認卡片的專案欄仍是同一個案子 |

## 額外要順手看的兩件事(不是 spec 列的,但值得確認)

- **確認鈕放著超過 60 秒再按**:提案 token TTL 只有 60 秒。預期仍會寫入成功,但訊息下方出現黃字警告「確認碼已逾時,系統用相同內容重新提案後才寫入」。若看到寫入失敗而非警告,就是重提案那段有問題。
- **重啟 dev server 後按舊卡片的確認鈕**:對話存在記憶體,重啟即清空。預期跳紅字「對話狀態已重置…請重講一次」,而不是靜默沒反應。

### 2026-08-14 第二輪:Kimi(moonshot-v1-32k)實跑

`.env.local` 的 Anthropic key 是空的,改用 Kimi 轉接層跑完 8 案。

| 案例 | 結果 | 實際行為 |
|---|---|---|
| 1 | ✅ | `search_projects → propose_log_note`,確認卡欄位正確 |
| 2 | ✅ | 0 筆候選 → `ask_clarification`,狀態「追問中」 |
| 3 | ✅ | 「旌旗」4 筆候選全列成按鈕(斗六/北屯/新竹/豐原) |
| 4 | ✅ | 取消 → 無寫入 |
| 5 | ✅ | 打字回「應該吧」→ 提案作廢、agent 反問,**沒有寫入** |
| 6 | 🟡 | 加規則後日期算對了(2026-08-19),但這一輪改成純文字反問、沒發提案,所以沒有確認卡片。加規則前算成 08-20(星期四,錯一天) |
| 7 | ✅ | 明確回「這個操作目前不支援,請用系統介面」,零工具呼叫 |
| 8 | ❌ | 「再幫我記一筆」仍重新呼叫 `search_projects`,沒沿用上一輪的 project_id(結果正確,只是多繞一趟) |

**Kimi 暴露、已在程式層修掉的兩個問題**(不是 Kimi 專屬,是「複述交給 LLM 自由發揮」的通病):

1. **把 confirmation_token 唸給使用者聽**(「確認碼是 7c72d66c-…,60 秒內有效」)。
   → 現在複述句只要含任何 UUID 就整句丟棄,改用系統自己生的說明,並跳警告。靠 prompt 交代不可靠,改成程式擋。
2. **講成「已經記了一筆」**,但當下根本還沒寫入;還會亂講 TTL(說一小時,實際 60 秒)。
   → system prompt 加規則 8(待確認語氣、不准提內部識別碼)、規則 9(追問一定要走 `ask_clarification`)、規則 10(日期算完自我覆核)。修完案例 2 從「已回覆」變成正確的「追問中」,token 不再外洩。

**還沒解決的**:規則加了之後 Kimi 措辭仍會出現「已經幫你記到…對嗎?」的混合時態;案例 8 的沿用行為改不掉。這兩個是模型能力,不是契約破口——確認卡片、寫入時機、token 都由 runtime 控制,沒有被影響。填入 Anthropic key 後值得再跑一輪對照。

### 2026-08-14 第三輪:補規則 + runtime 加固後重跑(仍是 Kimi)

| 案例 | 結果 | 變化 |
|---|---|---|
| 1 | ✅ | 不變 |
| 2 | ✅ | 不變 |
| 3 | ✅ | 不變 |
| 4 | ✅ | 不變 |
| 5 | ✅ | 打字回「應該吧」→ 重新提案,仍需按鈕,無寫入 |
| 6 | ✅ | 加規則 11 後會發提案了,確認卡片正常出現 |
| 7 | ✅ | 不變 |
| 8 | ❌ | 仍會重新 search,改不掉 |

**這一輪加的三道防線**(都在程式層或 prompt,不靠模型自律):

- **確認卡片的期限欄補上星期幾**(`2026-08-19(週三)`),星期幾由 runtime 從日期自己算。
  實測 Kimi 換算「下週三」約一半機率算成 08-20(那天是週四)——現在錯了會直接顯示在卡片上,
  使用者一眼看得出來,而不是等寫進系統才發現。
- **待確認訊息前綴「⏳ 還沒寫入,請確認:」**,由 runtime 寫死。
  Kimi 有相當比例會複述成「已經幫你記了一筆」,但當下根本還沒寫入;使用者若當真就不會去按確認,
  這件事等於沒發生而他以為做完了。prompt 規則擋不住(加了規則照犯),所以改由程式補一句不會說謊的話。
- **system prompt 規則 11**:要問「對嗎?」就一定要先呼叫 propose_*,否則使用者看不到確認按鈕。
  這條讓案例 6 從「純文字反問、流程斷掉」變成正常發提案。
