# Handoff Spec:PM 系統語音介面(Voice-to-PM Agent)

**版本**:v0.1 draft
**日期**:2026-08-11
**狀態**:待技術棧確認後補完(見「待決事項」)

---

## 1. Overview

### 目標

為自建專案管理系統(以下稱 PM 系統)建立語音介面,讓使用者以自然口語**紀錄資訊**與**提取資訊**。體驗基準對標 Grok in Tesla:對話回應延遲、可插話打斷、口語容錯。

### 核心架構原則(不可妥協)

1. **語音層是純轉譯層(description-space)**:STT / LLM / TTS 不持有業務狀態、不直接觸碰資料庫。
2. **所有讀寫走結構化工具面(causal-space)**:LLM 只能透過定義好的工具呼叫 PM 系統 API;驗證、權限、稽核全在 API 層。
3. **寫入必經確認**:任何會改變系統狀態的操作,執行前必須取得使用者口頭確認。讀取免確認。
4. **工具面以 MCP server 實作**:同一工具面未來可掛接文字介面、桌面 agent、其他客戶端,語音只是第一個消費者。

### 系統分層

```
┌─────────────────────────────────────────────┐
│  語音層(Pipecat pipeline)                    │
│  STT(streaming)→ VAD / barge-in → TTS(streaming)│
└──────────────────┬──────────────────────────┘
                   │ 純文字
┌──────────────────▼──────────────────────────┐
│  Agent 層(LLM + function calling)            │
│  意圖判斷、實體對齊、確認流程、對話狀態          │
└──────────────────┬──────────────────────────┘
                   │ 結構化工具呼叫(MCP)
┌──────────────────▼──────────────────────────┐
│  工具面(MCP server)                          │
│  參數驗證、權限檢查、稽核紀錄                   │
└──────────────────┬──────────────────────────┘
                   │ 內部 API
┌──────────────────▼──────────────────────────┐
│  PM 系統(既有,不因本專案改動核心邏輯)          │
└─────────────────────────────────────────────┘
```

| 包含 | 不包含 |
|------|--------|

即時多輪對話、barge-in 打斷、任務更新與狀態變更、電話入口(接單場景)。

## 3. 工具面規格(MCP Server)

### 設計約束

- 每個工具做**一件事**;參數最少化;禁止泛用 CRUD 端點(如 `patch_task`)。
- 讀取類工具:冪等、免確認。
- 寫入類工具:必須帶 `confirmation_token`(見 §5),API 層拒絕無 token 的寫入。
- 所有寫入落稽核紀錄:`{actor, timestamp, tool, params, source: "voice", transcript_ref}`。

### Phase 1 工具清單

| 工具 | 類型 | 參數 | 回傳 | 備註 |
|------|------|------|------|------|
| `search_projects` | 讀 | `query: string` | 候選清單 `[{id, name, status, client_name}]`,上限 5 筆 | 模糊比對;實體對齊的第一步 |
| `get_project_summary` | 讀 | `project_id` | 進度摘要、未完成任務數、最近 3 筆更新 | 回傳需為「可口語化」的精簡結構,勿回整包 |
| `list_tasks` | 讀 | `project_id, status?: open\|done\|all` | 任務清單(上限 10 筆 + 總數)| 超過 10 筆時回傳總數讓 LLM 摘要 |
| `create_task` | 寫 | `project_id, title, description?, due_date?, confirmation_token` | `{task_id}` | |
| `log_note` | 寫 | `project_id, content, tags?, confirmation_token` | `{note_id}` | 口述會議 / 現場紀錄的主要落點 |

### 工具回傳格式原則

回傳 JSON 需為 **TTS-friendly**:欄位精簡、預先排序、數量截斷。LLM 不應收到需要自行過濾的大 payload——這會拉高延遲與幻覺率。

## 4. 對話流程與狀態

### 4.1 口述紀錄流程(主場景)

```
使用者口述(可長段)
  → STT 全文轉寫
  → LLM 抽取:{目標專案(候選), 紀錄類型(task/note), 結構化內容}
  → 若專案不明確 → 追問(§4.3)
  → 口頭複述摘要 + 請求確認(§5)
  → 使用者確認 → 執行寫入 → 回報結果
  → 使用者否認 → 詢問修正 → 回到複述
```

### 4.2 查詢流程

```
使用者提問 → 實體對齊 → 呼叫讀取工具 → LLM 摘要為口語 → TTS 播出
```

讀取免確認,直接執行。

### 4.3 實體對齊(Entity Resolution)

| 情境 | 行為 |
|------|------|
| `search_projects` 回傳 1 筆且相似度高 | 直接採用,複述時帶出完整案名讓使用者有機會糾正 |
| 回傳多筆 | 唸出前 2–3 筆候選讓使用者選(「你是說王太太信義路的案子,還是王先生大里的?」)|
| 回傳 0 筆 | 告知找不到,詢問是否換個說法或是否為新專案(新專案建立不在 Phase 1 範圍,僅提示)|

**禁止**:LLM 自行猜測 project_id、憑記憶填入任何 id。所有 id 必須來自當輪 `search_projects` 回傳。

### 4.4 對話狀態機

| 狀態 | 進入條件 | 可轉移至 |
|------|----------|----------|
| `idle` | 啟動 / 完成一輪 | `listening` |
| `listening` | 使用者開始說話(VAD 觸發)| `processing` |
| `processing` | STT 完成 | `clarifying` / `confirming` / `responding` |
| `clarifying` | 實體不明確 | `listening` |
| `confirming` | 寫入前複述完成 | `executing`(確認)/ `clarifying`(否認)|
| `executing` | 取得確認 | `responding` |
| `responding` | 有結果可回報 | `idle` |

超時規則:`clarifying` / `confirming` 等待逾 15 秒無回應 → 提示一次;再逾 15 秒 → 放棄本輪、明確告知未寫入任何資料、回 `idle`。**逾時一律不寫入。**

## 5. 寫入確認機制

1. LLM 完成抽取後,以口語**複述關鍵欄位**:目標專案全名、動作(新增任務 / 記一筆紀錄)、標題或內容摘要、日期(若有)。
2. 同時由 Agent 層產生一次性 `confirmation_token`(綁定該次 payload 的 hash,TTL 60 秒)。
3. 使用者明確肯定(「對」「可以」「沒錯」)→ 帶 token 呼叫寫入工具。
4. 模糊回應(「嗯…」「應該吧」)→ 視為未確認,再問一次。
5. Payload 若在確認後被修改 → token 失效,必須重新複述確認。

此機制的目的:STT 在專有名詞上的錯誤率不可消除,確認層是防止髒資料進入系統的唯一防線。**任何繞過此機制的捷徑都是架構違規。**

## 6. 延遲預算(Latency Budget)

Phase 1 的口述紀錄場景對延遲要求較寬,查詢場景須符合以下預算:

| 階段 | 預算 | 備註 |
|------|------|------|
| STT(講完 → 文字)| ≤ 300ms | streaming STT,endpoint 判定含在內 |
| LLM 首 token | ≤ 400ms | 含工具呼叫時允許至 1.5s,但須先播「填充語」|
| 工具執行(PM API)| ≤ 200ms | PM 系統端 SLA;超過需回填充語 |
| TTS 首音訊 | ≤ 200ms | streaming TTS |
| **總計(無工具)** | **≤ 900ms** | 使用者講完 → 聽到第一個字 |

**填充語策略**:工具呼叫預期 > 800ms 時,先播短促自然的過場(「我看一下…」),避免死寂。過場語需多樣化(≥ 5 種輪替),不可每次相同。

## 7. 語音層規格

| 項目 | 規格 |
|------|------|
| Pipeline 框架 | Pipecat(Python)|
| STT | 需支援 zh-TW streaming;**驗收前必測**:台灣口音、中英夾雜(案名、品牌名)、室內設計術語(木作、放樣、監工)|
| TTS | zh-TW streaming、首音訊 ≤ 200ms;音色自然度以盲測 3 人以上過半接受為準 |
| VAD | 靜音 endpoint 閾值初設 800ms,可調參數化;口述紀錄場景放寬至 1.5s(使用者會停頓思考)|
| Barge-in | Phase 1 不實作,但 pipeline 選型不得阻擋 Phase 2 加入 |

### 專有名詞強化

維護一份**熱詞表**(hotword list):現有專案名、客戶姓氏、常用術語,注入 STT 的 keyword boosting(若供應商支援)。熱詞表由 PM 系統每日同步產生,不可手動維護。

## 8. 錯誤與邊界情況

| 情境 | 行為 |
|------|------|
| STT 回傳空白 / 信心度過低 | 「不好意思,我沒聽清楚,可以再說一次嗎?」不進入 LLM |
| LLM 工具呼叫參數驗證失敗 | API 層拒絕,Agent 重試一次;再失敗 → 告知使用者並建議改用文字介面,**不得默默吞掉** |
| PM API 逾時 / 5xx | 告知「系統暫時沒有回應,剛剛那筆**沒有**存進去」——失敗時必須明確告知未寫入 |
| 寫入成功但 TTS 前連線中斷 | 稽核紀錄為準;下次啟動時主動回報上次結果(需持久化 pending-report 狀態)|
| 使用者一句話含多個動作(「幫我記 A 也記 B」)| Phase 1:拆成多輪逐一確認執行,不做批次 |
| 環境噪音誤觸發 | VAD 信心度閾值 + 最短語音長度(< 300ms 的觸發丟棄)|
| 敏感操作誤入(刪除、改金額)| 工具面根本不存在此類工具,LLM 應回覆「這個操作目前不支援語音,請用系統介面」|

## 9. 驗收標準

### 工具調用層(先於語音獨立驗收)

- 準備 ≥ 30 句真實情境測試語句(涵蓋紀錄、查詢、模糊實體、多動作、不支援操作)。
- 工具選擇正確率 ≥ 95%;實體對齊(含追問後)成功率 ≥ 90%。
- 寫入類:無 confirmation_token 的呼叫 100% 被 API 層拒絕(以自動化測試驗證)。

### 語音層

- 查詢場景端到端延遲 p50 ≤ 900ms、p95 ≤ 1.5s(無工具呼叫)。
- 中英夾雜案名的 STT 辨識:熱詞表內名詞正確率 ≥ 90%。
- 確認流程:20 次寫入實測,0 筆未經確認落庫、0 筆確認後遺失。

### 稽核

- 隨機抽 10 筆語音寫入,稽核紀錄可完整回溯到原始轉寫文字。

## 10. 開發順序(建議 Milestones)

1. **M1 — 工具面**:MCP server + 5 個工具 + 驗證 / 稽核 / confirmation_token 機制,純 API 測試通過。
2. **M2 — Agent 層(文字)**:文字介面跑通全部對話流程與狀態機,通過 §9 工具調用層驗收。
3. **M3 — 語音掛載**:Pipecat 接上 STT/TTS,口述紀錄場景可用。
4. **M4 — 查詢場景 + 延遲調優**:達成延遲預算,通過語音層驗收。

M1、M2 與語音完全解耦——語音供應商選型可與 M1/M2 並行進行,不阻塞。
