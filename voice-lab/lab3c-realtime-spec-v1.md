# Lab 3c 規格 v1 — Realtime 流暢語音對話

**日期**:2026-08-15
**狀態**:規格定稿,待 Yen 開模型白名單後動工
**目標**:Yen 原話「像跟 ChatGPT 聊天模式一樣通順,像 Tesla 裡的 Grok 一樣流暢」。
這是正式產品目標,不是實驗——批次錄音管線(3a/3b)已實測證明達不到,本規格採用
OpenAI Realtime API 重做語音通道。

---

## 0. 為什麼批次管線到不了,不再試了

3a/3b 走的是「錄完→上傳→辨識→LLM→合成朗讀」,實測每輪 5-10 秒,結構性問題全數踩過:

| 實測踩到的問題 | 根因 |
|---|---|
| 靜音偵測誤切/誤擋(門檻怎麼調都有人中招) | 自己寫 VAD,對麥克風靈敏度做假設 |
| 辨識編造(無聲音檔生出「好的,將進行音響定位」) | 批次辨識拿不到對話上下文,只能靠提示詞,提示詞又變編造範本 |
| 片段錄音(Yen 的 8 秒錄音有 5 秒靜音) | 錄音-停頓判斷全在我們手上,硬體差異吃不掉 |
| 機器朗讀音、不能插話 | 架構天生如此 |

結論:**每輪 5-10 秒是架構下限,不是參數問題**。批次管線保留給打字模式(Lab 2,運作良好),
語音模式整條換掉。

## 1. 技術選型

| 項目 | 決定 | 理由 |
|---|---|---|
| API | OpenAI Realtime API(WebRTC) | ChatGPT 語音模式同源技術;延遲 0.3-0.8s;原生插話;支援 function calling |
| 模型 | `gpt-realtime-*-mini` 起步 | 約 $0.02-0.05/分鐘;以 5 人×10 分/天估約 NT$700-1,700/月,實際口述用量更低。品質不夠再升標準版(貴 3 倍),改一個字串 |
| 傳輸 | 瀏覽器 WebRTC 直連 OpenAI | 延遲最低;iPhone Safari 支援良好(3a 死在 SpeechRecognition,WebRTC 沒這問題) |
| 金鑰 | 後端 `POST /v1/realtime/client_secrets` 發短效金鑰 | 正式 API key 永不落地前端;短效金鑰過期自動失效 |
| 斷句 | OpenAI 伺服器端 VAD | **整段自寫的靜音偵測程式碼刪除**,不再維護 |
| 逐字稿 | 開啟 input_audio_transcription | 兩個用途:伺服器端口令比對、稽核回溯(handoff §8) |

### 連線流程(依 2026-08 現行 API 面)

```
瀏覽器                      我們的後端                    OpenAI
   │ GET /api/voice-live/token   │                          │
   │────────────────────────────>│ POST /v1/realtime/       │
   │                             │   client_secrets ───────>│
   │<──短效金鑰──────────────────│<─────────────────────────│
   │                                                        │
   │ RTCPeerConnection + 麥克風 track + data channel "oai-events"
   │ SDP offer → POST /v1/realtime/calls ──────────────────>│
   │<═══════════ 雙向音訊串流 + 事件通道 ═══════════════════>│
```

## 2. 鐵律移植表(最重要的一節)

Lab 2 的每條防線在 Realtime 下怎麼守,逐條交代,不含糊:

| Lab 2 鐵律 | Realtime 下的實作 | 強度 |
|---|---|---|
| LLM 沒有寫入工具 | 工具清單一樣只有 `propose_*`,commit 只存在於我們伺服器 | ✅ 不變 |
| 確認與否不由 LLM 判斷 | 使用者語音逐字稿(transcription 事件)送我們伺服器跑**同一套白名單比對**(`matchVoiceCommand`,含「不對≠對」防線);比對到「確認」才由伺服器 commit | ✅ 不變 |
| id 不可捏造 | project_id 仍須來自 search_projects 回傳;propose 時後端照樣驗 | ✅ 不變 |
| payload hash / token TTL / 冪等 | Lab 1 契約端點原封不動,工具呼叫經我們後端轉發 | ✅ 不變 |
| 確認卡片欄位由 runtime 生成 | propose 成功後,canonical payload 照樣渲染成螢幕卡片;同時把欄位文字塞回對話請模型口語複述 | ✅ 不變 |
| 稽核 | audit_log 照記,**加記語音逐字稿**(handoff §8:寫入可回溯到原始轉寫) | ✅ 強化 |
| **respond 閘門(沒查過就不准講)** | **守不住。** Realtime 模型直接對使用者說話,沒有「每句話過工具」的攔截點 | ⚠️ 降為軟性 |
| 閒聊擋阻 | 只剩 instructions 約束(軟性)。硬性防線縮到「說了也寫不進去」 | ⚠️ 降為軟性 |

### 這個取捨要 Yen 知情

流暢的代價:**我們放掉「模型每句話都被程式攔截」的控制,換取自然對話**。
模型可能會陪聊、可能講出沒查證的話。但真正不可逆的東西——寫入資料庫——防線一條沒放:
它嘴上怎麼講都沒用,寫入永遠要過 propose→伺服器比對「確認」→commit。

一句話:**嘴巴放開,手還是綁著的。** 若實測發現陪聊失控,退路是 instructions 加嚴 +
事後稽核逐字稿,不是回批次架構。

## 3. 工具面

沿用 8 工具中的 6 個,拿掉 2 個批次架構專用的:

| 工具 | 去留 | 理由 |
|---|---|---|
| search_projects / get_project_summary / list_tasks | ✅ 留 | 經後端轉發打 Lab 1 端點 |
| propose_create_task / propose_log_note | ✅ 留 | 兩階段寫入的前半 |
| ask_clarification | ✅ 留 | 多筆候選仍要結構化選項(螢幕按鈕 + 口語唸出) |
| respond / decline | ❌ 拿掉 | 它們存在是為了「強迫每句話過工具」——Realtime 模型直接說話,這兩個工具失去意義 |

工具呼叫路徑:模型發 function_call 事件 → 瀏覽器收到 → 打我們的
`POST /api/voice-live/tool`(帶登入 session)→ 後端驗證+轉發 Lab 1 端點 → 結果回填對話。
**前端只是傳話筒,不碰 VOICE_API_KEY、不做任何判斷。**

### 熱詞問題在 Realtime 下的處理

專案名(磐頂長老教會等)放進 session instructions 供模型對照。
3b 的教訓(提示詞變編造範本)在這裡風險較低——模型直接聽音訊、有完整對話上下文,
不是拿片段音檔瞎猜。但**驗收要專測**:講不存在的案名,看它會不會硬湊成清單裡的。

## 4. 語音確認流程(全語音、免手)

```
使用者:「幫我在磐頂記一筆,木作進場前先放樣」
  → 模型 function_call: search_projects → propose_log_note
  → 後端回 token + canonical payload
  → 螢幕:確認卡片(專案/動作/內容,runtime 生成)
  → 模型口語複述:「要記到磐頂長老教會:木作進場前先放樣,對嗎?」
使用者:「確認」
  → transcription 事件 → 我們伺服器 matchVoiceCommand()
  → 比對到 confirm → 伺服器 commit(帶 token)→ 寫入
  → 結果塞回對話,模型口語回報「記好了」
使用者:「應該吧」/「不對」/(旁人講話)
  → unclear / cancel / unclear → 一律不寫入
```

關鍵細節:
- **等待確認期間,模型的任何輸出都不觸發寫入**——寫入的唯一入口是伺服器比對成功
- 舊防線全沿用:「不對」含「對」不算確認、模糊詞一律 unclear、token 60 秒 TTL 逾時同 payload 重提
- 使用者在確認前講了別的內容 → 提案作廢(同 Lab 2)

## 7. 驗收

1. **延遲**:講完到聽到回應 < 1.5 秒(含工具呼叫)
2. **插話**:模型講到一半開口,它要停
3. **確認鐵律**:「應該吧」「嗯」「不對」× 各 3 次,零寫入;「確認」才寫入,audit_log 含逐字稿
4. **30 句真實情境**(紀錄/查詢/模糊實體/不支援操作),工具選擇正確率 ≥ 95%(handoff §9)
5. **假案名測試**:講清單裡沒有的案名,不得硬湊成現有專案
6. **手機實測**:iPhone Safari 經 https 通道全流程走通(3a 死掉的場景)
7. **斷線**:拔網路,提示明確、重連後對話可續
